# Internationalization (i18n)

Internationalization is a **basic requirement of the UI framework**, like accessibility
([ACCESSIBILITY.md](ACCESSIBILITY.md)). The framework is language-independent by construction. English
is the **source language**, not a hard-coded one: every user-visible text is a catalog entry, every
layout survives other languages, and a new language is a data file, not a code change.

This document is part of the framework (it lives in `src/ui-framework/docs/`) and contains no application
specifics. The New GUI inherits it by using the framework; the legacy GUI stays English-only and does
not change.

## What changes for the framework

| Area | Before | With i18n |
| --- | --- | --- |
| Strings | literals in code and in mockups | catalog entries with stable keys; English source |
| Layout | tuned to English lengths | grows, wraps or elides for any length (German is about 30 % longer) |
| Hints and status words | a closed English vocabulary | a closed vocabulary of keys, translated per language |
| Numbers, sizes, dates | one fixed format | formatted by the active locale |
| Plurals | hand-coded "file"/"files" | per-language plural rules |
| Fonts | one Latin font | a fallback chain per script, glyph coverage tested |
| Sorting and letter jump | alphabetical, English | language-dependent collation |
| Direction | left to right | logical start/end in layout, so right to left can be added |

## Requirements

**R1 No user-visible literals.** No string a user can read is written in framework or application code.
Text comes from a catalog by key. Data is not text: game titles, file names, network names and device
names are drawn as given. Log and debug output stays English and is not translated.

**R2 English is complete and the fallback.** The English catalog is compiled into the program. A key
missing in another language falls back to English; the UI never shows a key or a blank. The tests report
every missing key.

**R3 Whole sentences with named placeholders.** A message is one sentence with named arguments
(`Found {count} games on {drive}`), never fragments glued together, so a translator can reorder words.
Button names (A, B, the D-pad glyph, the layout's glyphs) are tokens inside the text and are never
translated; the action words around them are.

**R4 Plurals by language rules.** Counted messages carry the plural forms the language needs (one, few,
many, other). Hand-written plural code is not allowed.

**R5 Locale-aware formatting.** Numbers (decimal mark, grouping), sizes (unit labels from the catalog),
dates and times (12/24 hour, field order), relative ages ("5 min ago") and lists come from the active
locale through the framework's formatters (`formatBytes`, `formatAge`, `plural`, clock).

**R6 Layout survives text expansion.** No component depends on the length of a string. Labels elide with
an ellipsis, paragraphs wrap, rows grow (the Largest-text rule of the accessibility guide extends to
languages). Fixed-width text slots are not allowed; where a width is fixed (a hint bar, a tab row) the
component drops the least important items, never clips. A pseudo-locale (accented and about 40 % longer)
is part of the standard tests.

**R7 Fonts cover the script.** The font chain covers every glyph of every shipped language; a missing
glyph is a test failure, never a silent blank box. Fonts for further scripts are optional downloads (the
existing font download mechanism is the model), verified like any other download.

**R8 Direction-ready layout.** Components describe layout with start and end, not left and right:
marker bar at the start edge, scroll bar at the end edge, progress fills from the start, tab order,
value alignment. Focus movement keeps its physical meaning (the Left button moves left) but lists with
a start/end structure mirror. Right-to-left is not required for the first release; the layout must not
rule it out.

**R9 Hints are translated as a vocabulary.** The closed hint and status vocabularies are keys
(`hint.back`, `switch.on`). One word per concept in every language, as in English. The hint-bar
fitting works on the translated text.

**R10 Collation is a service.** Alphabetical order and the letter-jump groups are language-dependent
(ä, å, ñ, ch). The framework defines a `Collator` interface (compare, group letter); the application
chooses its data ordering and may keep a neutral order for titles.

**R11 The language is a user setting.** Shown with native names ("Deutsch", "Français"), chosen once in
the first-run flow and changeable in Settings. Switching is live: swap the catalog and repaint, no
restart.

**R12 Plain language in every language.** The accessibility rules on plain language, sentence case and
"enough text where needed" apply per language and are part of translation review.

## Design

### Catalog

- **Key scheme:** semantic, dotted, stable keys: `hint.back`, `switch.on`, `modal.error.tryAgain`.
  Each key has an English source text and a **translator note** (context, where it appears, length
  limit, what the placeholders are). English-as-key is not used: it breaks when wording changes and
  cannot distinguish "Back" the action from "Back" a position.
- **Format:** UTF-8 text files, one per language, `key = text` with plural forms and `#` notes; parsed
  once when the language is chosen. The English source is generated into the program as a table.
- **Ownership:** the framework ships catalogs for its own vocabularies (`ui.*`: hints, status words,
  units, modal structure texts, phase phrases) in English and in every language the project ships. The
  application ships its own (`app.*`). The loader merges them; keys cannot collide across namespaces.
- **Location and delivery:** language files live next to the program's data under
  `/media/fat/mister-pat/`, are installed by the updater from the release package with the same hash
  verification as other downloads, and are read once at selection time (no reads in the render path,
  one write per install, SD-card friendly).
- **Memory:** only the active language is loaded, as one contiguous block plus an index; bounded by a
  size limit.

### Implemented today: `ui::format`, `ui::plural`, `ui::position`, `ui::joinParts` (src/ui-framework/kit/Text.h)

The one placeholder syntax is `{1}`, `{2}`, ... `{9}` (1-based, in the order of the call's arguments; a
translation may reorder them). There is no other syntax (no `%1`) and no per-tab helper: a tab never writes its
own fill function.

```cpp
ui::format("grid.info", {view, "3 of 42"});          // the catalog sentence with its placeholders filled
ui::fillTemplate(text, {a, b});                      // the same for a sentence already read from the catalog
ui::plural("arcade.empty.found", n, {working});      // key.one when n == 1, else key.other; {1} is n, extras {2}...
ui::position(3, 42);  ui::position(3, 500, true);    // "3 of 42", "3 of 500+" (format.position = "{1} of {2}")
ui::joinParts({system, year, players});              // the non-empty parts with " · " between (format.parts)
```

A `{` that does not start `{digit}` is text. A placeholder with no argument stays as written, so a missing
argument is visible instead of silently empty. Names with letters are not used because the pseudo-locale
rewrites letters. English has two plural forms (`.one`, `.other`); the language files will bring the others.

### API sketch

```cpp
struct Text;                                   // what components accept for user-visible text
Text   key(TextId id);                         // a catalog entry, resolved at draw time
Text   key(TextId id, Args args);              // with named placeholders; formatted when state changes
Text   plural(TextId id, long n, Args args);   // plural rules of the active language
Text   data(std::string_view s);               // data drawn as given (a title, a file name)

struct Locale { const char *code; /* "de" */ NumberFormat numbers; DateFormat dates;
                bool clock24; Direction direction; const Collator *collator; };
const Locale &locale();
void setLanguage(const char *code);            // swaps catalog and locale, requests a full repaint
```

Components take `Text`, never a raw string. Resolving a key returns a view into the catalog and does not
allocate. Formatting with arguments allocates, so it runs when the state changes and the result is cached
in the component's state, never per frame (the framework's no-allocation-in-render rule).

### Pseudo-locale and tests

- **Pseudo-locale** (`en-XA`): every letter accented, every text about 40 % longer, wrapped in markers
  (`[!! Ĝéţţíñĝ ýöûŕ ĝàmêš ŕéàðý !!]`). It exposes literals (they stay un-accented), clipping and fixed
  widths at a glance.
- **Locale matrix in the gallery:** every component and state renders in English, the pseudo-locale and
  the longest real translation, at 100 / 115 / 130 % text, in the same fit tests as the accessibility
  guide.
- **Lint (`tools/check-ui.sh`):** fails on a user-visible literal in `src/ui-framework/` and `src/app/` (a macro marks
  intended exceptions, such as log text), on a missing key, on a placeholder mismatch between languages,
  on an invalid plural form, and on an unused key. A completeness report per language.
- **Glyph test:** every catalog string of every language is checked against the font chain.
- **Direction test:** when right-to-left is enabled, the gallery renders mirrored layouts.

### Fonts and scripts

- The shared default font covers the Latin scripts; whether it covers Cyrillic and Greek is to be
  checked, and a fallback chain (primary font, then script fonts) is part of the font component.
- Complex shaping (Arabic, Indic scripts) needs a shaping engine and is **out of scope for the first
  release**. CJK needs large fonts (megabytes) and rules for line breaking without spaces; also later.
- The first release targets Latin-script languages, with Cyrillic and Greek if the fonts allow.

## Consequences for components

- Every component page gets a **Strings** section: the keys it owns, English source text, translator
  note, length limits (none should be fixed). Mockups stay in English and say so.
- The page template's "Largest text and high contrast" section becomes "Largest text, other languages and
  high contrast"; where it matters, a mockup shows the German-length variant.
- Hints, status words, phase phrases, modal and empty-state structure texts, units and the formatters are
  the framework's own catalog.
- `Hints` fitting, `TabRow`, `Badge` and the top bar are the places most exposed to expansion; they get
  explicit long-label states in the gallery.
- `formatButtonLabels`-style token handling moves into `Hints`/`TextBlock`: translated strings contain
  logical button tokens, formatted at render time for the user's layout.

## Open questions

- Does the shared default font cover the planned scripts, and which fallback fonts are needed?
- How are translations contributed and reviewed (data files in the repository, reviewed for plain
  language)? Credits follow the project's own rules.
- Which texts are data rather than UI (for example technical "Details" lines with raw error text)?
  Proposal: the label "Details" is translated, the raw technical text is shown as given.
- Spoken output (accessibility question 1) would need the language as well.
